**Q2 — D3 Cited-Number Table**

A direct numerical table comparing SAGE’s `105.6 µs` modeled cutover-evidence latency with Cox’s published millisecond switching result would be a methodological trap.

The values are not necessarily the same construct:

- SAGE reports event-based simulator measurements and warns that its experiment is not an absolute benchmark at `docs/paper/paper.tex:1587`.
- Its `105.6 µs` value is specifically “cutover-evidence latency” at `docs/paper/paper.tex:1600`.
- Cox’s reported switching time may encompass checkpoint formation, engine startup, state transfer, network communication, recovery, or another end-to-end interval.
- Hardware, validator count, network topology, workload, cryptography, implementation language, and measurement boundaries differ.
- Presenting the numbers side by side invites an invalid inference that SAGE is faster.

I would split D3:

- **D3a — Required:** strengthen labels throughout RQ1 so “Cox-inspired control,” “Cox-threshold transplant,” and “BFT-SMaRt-style analogue” cannot be mistaken for independent implementations.
- **D3b — Conditional:** add an “as reported by original authors” evidence table only if it records experimental context and metric definitions, not a winner or speed ratio.

A legitimate format would be:

| System | Source | Implementation provenance | Metric reported | Measurement boundary | Configuration | Reported result | Cross-study comparable? |
|---|---|---|---|---|---|---|---|
| Cox | Cox authors | Original implementation | End-to-end switch time | Exact source definition | Exact source setup | Source value | No |

The caption must say these numbers characterize published operating points and **must not be used for performance ranking**. If that caveat makes the table unhelpful, omit the numbers and use a protocol/evidence table instead.

**Q3 — Is A Real Implementation Necessary?**

A real head-to-head is not logically necessary for the protocol’s scientific contribution to stand. The heterogeneous-boundary construction, rollback semantics, safety argument, bounded model checking, conformance evidence, and observed-fork controls can form a contribution without outperforming Cox.

However, D2 plus D3 cannot support an empirical claim that SAGE outperforms SOTA. They can support only:

- a scope claim: SAGE handles a boundary outside Cox’s stated applicability;
- a feature claim: SAGE adds bounded, verifiable rollback;
- an assurance claim: SAGE supplies bounded model checking and executable/conformance evidence not reported by the compared papers;
- an internal-cost claim: the added mechanism has modest overhead relative to controls implemented in the same harness.

A hostile reviewer could still reject because:

- no independent SOTA artifact validates comparative performance;
- the controls may encode assumptions favorable to SAGE;
- “Cox-threshold” at a heterogeneous boundary tests a transplanted quorum rule outside Cox’s supported scope, not Cox itself;
- absence of a property in a paper is not proof that its system “cannot” provide it;
- bounded TLC and bounded Rust correspondence are not a general mechanized proof;
- observed forks in deliberately weakened controls do not demonstrate that a faithful Cox deployment forks.

That last point is especially important. Avoid “SAGE is safer than Cox.” The defensible statement is: **Cox does not claim to solve this heterogeneous crossing; transplanting its checkpoint threshold into SAGE’s heterogeneous setting does not establish the required cross-boundary intersection.**

D4 becomes submission-blocking only if the target venue or mentor insists on empirical SOTA performance superiority. If the claimed contribution is a new safety mechanism with formal and executable evidence, it remains optional but high-value.

Also, BFT-SMaRt is probably the wrong first real implementation. It is membership reconfiguration within one engine, not the closest protocol-switching competitor. Integrating it would validate the distinction already stated at `docs/paper/paper.tex:327`, but would not answer the strongest “closest SOTA” challenge. Priority should be:

1. released Cox artifact, if obtainable and reproducible;
2. Spectrum or ADAPT artifact, if their mechanism and code are suitable;
3. BFT-SMaRt only as a real reconfiguration-class reference.
